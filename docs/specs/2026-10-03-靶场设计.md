## 一、目标与成功标准

### 目标

发布一个 **GitHub Template Repository**，社团成员 "Use this template" 后，在一个月内各自完成一款 **3–10 分钟的可玩 2D 小游戏**。

### 成功标准（按优先级）

| 级别 | 标准 |
|---|---|
| **能跑** | clone 下来 → Godot 4.7.2 打开 → 按 F5 → 进入标题画面，零报错 |
| **能玩** | 一条完整的核心循环：移动 → 交互 → 对话 → 接任务 → 完成 → 拿道具 → 结算 |
| **能改** | 换地图、换角色图、改台词、改任务名，**一行代码都不用写** |
| **能加** | 有能力的人能在**预留的钩子处**加一个自己的机制，20–40 行代码 |
| **能交** | 全员都能导出 Windows 版本并演示 |

### 关键约束（不可违反）

- **Godot 4.7.2 标准版**（不是 Mono 版）。Dialogue Manager 4 要求 Godot 4.6+，全员版本必须一致
- **GL Compatibility 渲染器** —— 2D + Web 导出 + 老硬件兼容，且是 Web 导出唯一支持的渲染器
- **中文字体必须打包进项目** —— Godot 的系统字体兜底**不支持 Web**，不打包的话 Windows 正常但 Web 全是豆腐块
- **插件全部打包进 `addons/`** —— 成员不做任何安装动作
- **全程不升级引擎、不升级插件**

## 二、靶场形态：它本身就是一款能通关的小游戏

**这是整个设计的核心决策，也是和原始方案最大的分歧点。**

原始方案的思路是"靶场给骨架，成员把 5 个插件拼起来"。但目标是"**10–30 人、基础参差、每人都必须交付**"，这条路走不通——30 人里只要有 5 个人倒在插件集成上，社长就被答疑吃光了。

**最终形态**：靶场自己就是一个**完整、可通关、约 5 分钟**的校园小游戏。

```
标题画面 → 出生点 → 探索校园 → 遇到 NPC → 按 E 对话
   → 接下任务 → 去另一处 → 完成任务 → 拿到道具
   → 触发结局 → 结算画面
```

**一个组什么都不改，这个流程也是"能玩、能展示"的。**

### 成员的两条路

| 路子 | 做什么 | 门槛 |
|---|---|---|
| **换内容** | 换地图、换立绘、改台词、改任务名 | 零代码或极少代码 |
| **加机制** | 围绕关键词做一个自己的机制 | 20–40 行代码，在预留钩子里写 |

**两条路不是限制，是省事通道。** 成员完全可以改 `scripts/`、`scenes/`、`assets/` 里的任何东西——群里还有更厉害的人。靶场的责任是**代码写得让人看得懂**（注释充分、不用奇技淫巧），而不是拦住人。

### 题材与关键词

- **题材**：大学校园，2D 俯视角
- **关键词**：**待定**（社长后续填写）。示例内容设计成**关键词无关**，这样换关键词不用重做场景

### ⚠️ `.gdignore` 的正确用法（已实测验证）

**实测结论**：
- 放在**项目根目录** → **不生效**（Godot 只对子文件夹认这个文件）
- 放在**子文件夹里** → **生效**，Godot 完全跳过该文件夹（不扫描、不导入、FileSystem 面板不显示）

**放置规则**：

| 文件夹 | `.gdignore` | 原因 |
|---|---|---|
| `content/dialogues/`、`content/quests/` | **绝对不要** | 这些是游戏运行时必须读取的资源 |
| `docs/` | **要** | 纯给人看的文档 |
| `wip/` | **要** | 原始素材，不该进游戏也不该被导出 |

**原始素材（PSD、Aseprite 源文件、下载的素材包）建议直接放在项目文件夹外面**——例如 `D:\Projects\NEUQ-GameJam-artwork\`。这样绝对不会被 Godot 扫到、不会污染 git 仓库。

### 脚本（`scripts/`）

| 文件 | 作用 | 预估行数 |
|---|---|---|
| `autoload/game_state.gd` | 全局状态：玩家位置、任务进度、已解锁区域、已获得道具 | ~40 |
| ~~`autoload/scene_manager.gd`~~ | ~~场景切换 + 淡入淡出~~ **删掉这一行——改用 Maaack 的 `SceneLoader`（自带加载画面、进度条、错误处理），不重复造轮子** | 0 |
| `world/test_map.gd` | 地图初始化、放置玩家到出生点 | ~30 |
| `player/player.gd` | 4 方向移动 + 动画 + 检测当前可交互对象 | ~70 |
| `npc/npc_base.gd` | NPC 基类：被交互时触发对话、根据状态改行为 | ~50 |
| `components/interactable.gd` | **交互中枢**。串起 对话 → 任务 → 道具 → 结算 的流程 | ~80 |
| `components/inventory.gd` | **手写背包**（不用 GLoot）。一个 `Array` + 增删查 | ~50 |
| `hooks/game_hooks.gd` | **★ 扩展点**。5 个空函数 + 注释 + 示例 | ~60 |

**总计约 435 行。** 这个规模是有意的——社长是初学者，且要能对 30 人答疑，代码量必须能"整个装进脑子"。

### 交互流程（`interactable.gd` 是核心）

```
玩家 Area2D 进入 NPC 的交互范围
        ↓
HUD 显示"按 E 交谈"
        ↓
玩家按 E → player.gd 调用当前对象的 interact()
        ↓
interactable.gd 判断这个 NPC 该干什么：
        ↓
  ┌─────┴─────┐
  ↓           ↓
播放对话    检查任务状态
  ↓           ↓
Dialogue Manager → 对话里用 `$>` 调用 QuestSystem 方法
  ↓
任务完成 → inventory.gd 加道具 → game_state 记录
  ↓
满足结局条件 → SceneLoader（Maaack）切到结算画面
```

## 五、扩展点设计（"加一个自己的机制"）

**这是"轻量代码的创造体验"能不能成立的关键。**

在 `scripts/hooks/game_hooks.gd` 里预留 **5 个空函数**，每个都带完整注释和示例：

```gdscript
## 【钩子 1】玩家做了某件事时被调用
## 用途示例：让 NPC 记住玩家做过什么
## 改这里，就能让世界对玩家的行为做出反应
func on_player_action(action_name: String) -> void:
    pass  # ← 在这里写你的代码

## 【钩子 2】对话开始时被调用
func on_dialogue_started(npc_name: String) -> void:
    pass

## 【钩子 3】任务状态变化时被调用
func on_quest_updated(quest_id: String, state: int) -> void:
    pass

## 【钩子 4】获得道具时被调用
func on_item_gained(item_id: String) -> void:
    pass

## 【钩子 5】每帧调用（慎用，会一直跑）
func on_tick(delta: float) -> void:
    pass
```

配套在 `docs/03-加机制指南.md` 里写 **5 个完整配方**，每个 20–40 行，例如：

| 配方 | 说明 | 难度 |
|---|---|---|
| NPC 复读玩家上一次做的事 | 用钩子 1 记录 + 修改对话 | ★ |
| 玩家走过的地方留下痕迹 | 钩子 1 + 生成节点 | ★★ |
| 同一个 NPC 第二次对话内容不同 | 钩子 2 + GameState 计数 | ★ |
| 计时压力 | 钩子 5 + 倒计时 UI | ★★ |
| 重复同一个动作会累积效果 | 钩子 1 + 计数器 | ★★ |

## 六、关键技术决策汇总

| 决策项 | 取值 | 理由 |
|---|---|---|
| 引擎版本 | **Godot 4.7.2 标准版** | DM4 要求 4.6+；不用 Mono 版（GDScript 项目不需要，且会造成缓存差异） |
| 渲染器 | **GL Compatibility** | 2D 最佳；老硬件兼容；**Web 导出唯一支持** |
| 设计分辨率 | **1280×720** | 16:9 通用；比 640×360 更能容纳来源不一的素材 |
| 拉伸模式 | `canvas_items` + `expand` | 已设 |
| 中文字体 | **立夏黑体（Sumr Sans）**，SIL OFL 1.1 | 简体覆盖 6763 字；黑体适合 UI；已打包并随附 LICENSE |
| 输入映射 | 自定义 `move_up/down/left/right` + `interact`（E） | **不用内置 `ui_*`**——那些同时是菜单导航键，且无法做按键重绑定 |
| 插件数量 | **4 个**（含待定的 godot_ai） | 插件数量是风险上限，不是功能上限 |
| 背包实现 | **手写 ~50 行**，不用 GLoot | GLoot 有未回应的严重 bug；手写代码是教学材料 |
| 相机跟随 | **内置 `Camera2D`**，不装插件 | 内置已自带平滑跟随和边界限制 |

### ⚠️ 已知的连带影响

40×30 的地图，若瓦片 32px，则地图共 1280×960 像素，**比 720 高的视口大**。因此**必须给玩家加跟随相机**，否则看不到全图。这会在"玩家移动"那一步一起做。

### ⚠️ Maaack 菜单套件带来的设计变更（2026-10-03 追加）

Maaack's Menus Template 会**接管菜单层和场景切换层**，带来 3 个 autoload：

```
SceneLoader                 ← 场景切换 + 加载画面 + 进度条 + 错误处理
ProjectMusicController      ← 跨场景背景音乐 + 轨道混合
ProjectUISoundController    ← 自动给按钮/滑块挂音效
```

**因此的三处变更：**

1. **原计划的 `scripts/autoload/scene_manager.gd` 取消** —— 用 `SceneLoader` 替代，它自带加载画面、进度条、错误处理，比我手写的 40 行强。**不要两套系统并存。**
2. **标题画面和结算画面改为配置 Maaack 的菜单场景**，不自己从零做。我们只需要：把"开始游戏"按钮指向我们的游戏场景，把结算画面接上。
3. **音乐和 UI 音效白捡** —— 原计划手写音频管理，现在可以直接用它的控制器。

**⚠️ 施工顺序必须调整**：菜单层本来在原计划的**阶段 7**，现在**必须提前到阶段 1 之前或紧随其后**。理由：如果先把游戏跑起来、最后才接菜单，就要回头改主场景、改场景切换逻辑、改暂停行为——**返工量远大于一开始就按它的框架来**。

**⚠️ 不要碰 `maaacks_menus_template` 里的示例场景**，它们会和你自己的场景混淆。要先读它自带的文档，搞清楚哪些是必须的、哪些是演示。

## 七、明确不做的事（YAGNI）

原方案或直觉上想要、但**明确决定不做**的：

| 不做 | 原因 |
|---|---|
| 存档 / 读档 | 5 分钟的小游戏不需要 |
| GLoot 背包系统 | 见上，手写 50 行足够 |
| RPG Components 2D | 见 `02-插件决策记录.md`，单人维护、0 用户、装不进 4.7 |
| 场景过渡插件 | 20 行代码的事 |
| 音频管理插件 | 20 行 autoload 的事 |
| 3 个以上场景 / 多个区域 | 关键词规则本来就要限制"3 个场景以内" |
| 战斗系统 | 本期核心循环选的是"探索 → 对话 → 任务"，不是战斗 |
| 多语言 / 本地化 | 只有中文 |
| 移动端导出 | 只做 Windows + Web |

## 八、施工顺序（分层交付）

| 层 | 内容 | 方式 |
|---|---|---|
| **第 1 层** | 地图、玩家移动、交互、对话 | **AI 带着社长一步步写，社长要学会** |
| **第 2 层** | 任务系统、NPC 状态机、背包、结算画面 | AI 写 + 逐行讲解 |
| **第 3 层** | 字体配置、目录整理、`.gdignore`、导出配置、README | AI 全写 |

**分层的理由**：社长选了"我要学会"。但按一步一确认的节奏，全部自己写要 20–40 轮对话，可能拖垮社团时间表。第 1 层是**最核心、最需要理解**的部分，学会它就能给成员答疑；第 2、3 层是装配和配置，理解成本高、学习收益低。
